# 文档模块开发进度记录

## 1. 文档说明

本文档用于记录当前 `document` 模块的开发进度，仅聚焦文档管理相关能力，不展开记录知识库管理、成员管理、问答模块和向量检索模块。

当前时间点：

- 日期：`2026-04-24`
- 当前正在开发模块：`apps/backend/src/modules/document`

本文档重点说明：

- 当前阶段正在开发什么
- 文档模块的计划步骤
- 当前已经实现了什么

## 2. 当前开发阶段

当前 `document` 模块处于：

- **第一阶段：文档业务模块骨架搭建与首批接口落地**

当前阶段目标是先把“文档元数据管理 + 文件落盘 + 基础权限接入”打通，先形成一个可继续迭代的业务闭环，再逐步接入异步解析、切块、向量化和问答链路。

当前阶段暂不追求一次性完成完整 RAG 流程，而是先落实以下基础能力：

- 文档模块目录结构
- 文档接口控制器
- 文档服务层
- 本地文件存储抽象
- 与知识库权限 Guard 的复用接入
- 文档资源级权限判断的基础框架

## 4. 当前已实现的功能

### 4.1 模块结构

当前已经创建：

```text
apps/backend/src/modules/document/
  dto/
    list-documents.dto.ts
    upload-document.dto.ts
  document.controller.ts
  document.module.ts
  document.service.ts
```

同时新增了本地文件存储抽象：

```text
apps/backend/src/common/storage/
  file-storage.module.ts
  file-storage.service.ts
```

### 4.2 已落地接口

当前已经实现以下接口：

1. `POST /api/knowledge-bases/:kbId/documents`
   - 上传文档
2. `GET /api/knowledge-bases/:kbId/documents`
   - 获取文档列表
3. `GET /api/knowledge-bases/:kbId/documents/:documentId`
   - 获取文档详情
4. `GET /api/knowledge-bases/:kbId/documents/:documentId/download`
   - 下载文档原文件
5. `DELETE /api/knowledge-bases/:kbId/documents/:documentId`
   - 删除文档
6. `POST /api/knowledge-bases/:kbId/documents/:documentId/reparse`
   - 手动触发重解析入口

### 4.3 已实现的业务能力

当前已经实现：

- 文档模块已注册到 `AppModule`
- 文档接口已接入 `AuthGuard`
- 文档接口已复用知识库 `KbPermissionGuard`
- 上传接口已支持基础文件校验
- 上传接口已支持本地磁盘落盘
- 上传接口已支持文档元数据写入 `b_documents`
- 已支持生成文件哈希 `SHA-256`
- 已支持文档列表分页、状态筛选、关键字筛选
- 已支持查询单个文档详情
- 已支持原文件下载
- 已支持删除文档及本地文件清理
- 已支持重解析时清理 `b_document_chunks` 并重置文档状态

### 4.4 已复用的权限体系

当前文档模块没有重新发明一套权限逻辑，而是直接复用了知识库模块已有能力：

- `@KbPermission(...)`
- `KbPermissionGuard`
- `KbPermissionService`

当前接入策略如下：

- 上传：使用 `uploadDocument`
- 列表与详情：使用 `read`
- 下载：使用 `downloadDocument`
- 删除与重解析：先通过知识库级可读权限，再在服务层补充文档资源级权限判断

### 4.5 已实现的本地文件存储能力

当前文件存储采用本地磁盘方案，便于先快速打通开发链路。

当前实现特点：

- 存储根目录为 `apps/backend/storage`
- 文档按知识库 ID 分目录存放
- 文件名使用时间戳 + UUID 生成
- 支持文件写入
- 支持文件存在性校验
- 支持文件流读取
- 支持删除本地文件

这部分已经具备后续替换为 OSS / MinIO 的基础抽象能力。

## 6. 当前实现的边界说明

为了避免误解，需要明确当前 `document` 模块还只是**业务层第一版**：

- 当前“重解析”只是重置状态和清理旧分块入口
- 当前“上传成功”不代表已经可检索
- 当前“下载”是直接回传源文件，不涉及权限审计日志
- 当前“删除”只处理数据库记录和本地文件，不处理向量库
- 当前“资源级权限”已经有基础框架，但还需要在后续流程中继续细化

## 7. 建议下一步优先完成什么

建议下一步优先进入：

### 7.1 第一优先级：`document-processing` 模块

建议新增独立模块，例如：

- `apps/backend/src/modules/document-processing`

优先承接：

- 入队
- 文本提取
- 切块
- 状态回写

原因：

- 当前 `document` 模块已经具备上传和重解析入口
- 下一步最关键的是让文档真正进入“可处理、可解析”的状态

### 7.2 第二优先级：`ai` 模块中的 Embedding 能力

建议后续将以下能力放到 `ai` 模块：

- Embedding 模型调用
- LLM 调用
- Rerank 调用

原因：

- `document` 模块不应该直接承载模型调用细节
- 这样便于后续问答模块和文档处理模块共同复用

### 7.3 第三优先级：补齐文档资源级权限

建议继续完善：

- `owner / manager` 可管理任意文档
- `collaborator` 仅可删除和重解析自己上传的文档
- `member / publicVisitor` 不能删除和重解析

原因：

- 当前这部分已经有基础结构
- 继续完善后，文档模块就能和知识库成员权限设计完全对齐

## 8. 当前结论

当前 `document` 模块已经完成了**第一阶段基础闭环**：

- 模块已建好
- 路由已建好
- 服务已建好
- 本地文件存储已打通
- 知识库权限复用已打通
- 文档删除与重解析入口已具备

但它还处于“**RAG 流程前置准备阶段**”，离真正可解析、可向量化、可问答还有明显的后续工作。

因此，当前最合理的推进顺序是：

1. 保持 `document` 模块继续只负责文档业务
2. 新增 `document-processing` 模块负责异步解析流程
3. 新增或完善 `ai` 模块负责模型能力
4. 最后再接知识库问答链路

这样可以保持模块边界清晰，也最利于后续持续扩展。
