# RAG系统优化实践与调优策略

## 一、文档处理优化

### 1.1 分块策略对检索质量的影响

分块（Chunking）是文档处理中最关键的预处理步骤。分块质量的优劣直接影响下游检索的效果。

**分块大小选择**：
- 太小（<100 tokens）：语义信息不足，难以被检索到，但精度高
- 中等（200-500 tokens）：语义完整性和粒度平衡最佳，是RAG场景的首选
- 太大（>1000 tokens）：包含过多无关信息，降低检索精度，但上下文更丰富
- Linsor AI采用三层粒度策略：Level 1（根块，约1200 tokens）用于最终上下文，Level 2（中块，约500 tokens）用于向量检索，Level 3（子块，约300 tokens）用于精确匹配。检索时命中L3后自动展开为L1的完整内容（Small-to-Big策略）

**分块重叠（Overlap）**：
在相邻分块之间设置一定的文本重叠（通常10-20%），避免关键信息恰好落在分块边界上被截断。重叠过大则信息冗余度高，过小则边界问题严重。

**结构化感知分块**：
Linsor AI的`structured-token-aware`策略考虑了多种文档结构特征：
- Markdown标题层级（H1-H6）→ 设置sectionLevel元数据
- 代码块边界 → blockType标记为"code"
- 表格 → blockType标记为"table"
- 列表边界 → 保持列表项的完整性

结构感知分块在RRF融合阶段获得质量乘数加成（×1.02到×1.10），因为结构化内容通常比无结构文本更具信息密度。

### 1.2 Embedding模型选择

不同场景适合不同的Embedding模型：

| 模型 | 维度 | 最大输入 | 适用场景 |
|------|------|----------|----------|
| text-embedding-v4（阿里云百炼） | 1024 | 8192 tokens | 中文文档、通用文本 |
| BGE-M3（BAAI） | 1024 | 8192 tokens | 多语言、混合检索（稠密+稀疏一体） |
| text-embedding-3-large（OpenAI） | 256-3072 | 8191 tokens | 英文文档、需要高维度表示的场景 |
| Jina Embeddings v3 | 1024 | 8192 tokens | 多语言、长文档、支持任务特定LoRA |

选择建议：中文为主选text-embedding-v4或BGE-M3；多语言场景选BGE-M3；纯英文选text-embedding-3-large。维度选择方面，1024维在大多数场景下已足够，3072维仅在需要极致精度的场景下使用。

### 1.3 文档解析质量

PDF解析是最大的挑战。推荐使用：
- **Mammoth**：将.docx转为Markdown，效果好
- **PyMuPDF**：PDF文本提取，速度快
- **pdf-parse**：Node.js的PDF解析库
- **Unstructured.io**：支持30+格式的综合解析工具
- **pdfexcavator**：Linsor AI使用的自定义PDF解析器，专门处理中文PDF和表格

对于Markdown文档，使用gray-matter解析frontmatter元数据，保留完整的标题层级结构。代码文件按函数/类边界分块，保留import语句和注释。

## 二、检索效果优化

### 2.1 查询改写策略

查询改写是提升检索效果最有效的手段之一。核心改写策略包括：

- **去口语化**："这个东西怎么用啊？" → "XX工具的使用方法"
- **补充上下文**："和MySQL比呢？"（多轮场景）→ "XX数据库与MySQL的性能对比"
- **拆解复合问题**："Doris和ClickHouse在查询性能和存储成本上有什么区别？" → 拆解为两个子查询
- **多角度改写**：从不同角度改写同一问题（性能角度、成本角度、使用场景角度）

改写模型选择：使用轻量模型（如qwen-turbo）进行改写，延迟通常<500ms，对用户体验影响极小。只在改写失败时回退到原始查询。

### 2.2 检索参数调优

| 参数 | 作用 | 典型值 | 调大效果 | 调小效果 |
|------|------|--------|----------|----------|
| denseTopK | 稠密检索返回数量 | 20-30 | 提高召回率，增加后续计算量 | 降低召回率，提升速度 |
| sparseTopK | 稀疏检索返回数量 | 20-30 | 同上 | 同上 |
| fusionTopK | RRF融合后保留数量 | 50-80 | 为重排提供更丰富的候选池 | 减少重排计算量 |
| scoreThreshold | 相似度最低阈值 | 0.15-0.3 | 保留更多候选（宽松） | 过滤更多噪声（严格） |

按问题类型的动态调整策略：
- **事实查询（fact_lookup）**：denseTopK=20, sparseTopK=20, fusionTopK=50, scoreThreshold=0.3。使用较严格的过滤，因为事实查询需要精确匹配
- **对比分析（compare_analysis）**：denseTopK=30, sparseTopK=30, fusionTopK=80, scoreThreshold=0.15。放宽过滤门槛，扩大候选池，因为对比分析需要覆盖多个对象的多个维度
- **开放研究（research_or_open_world）**：使用与对比分析相同的宽松参数，确保不遗漏相关信息

### 2.3 Rerank精排调优

Rerank是决定最终检索质量的最后一道关：

- **单查询评分 vs 多查询评分**：事实查询使用主查询单独评分。对比分析和研究类问题使用多查询分别评分取最大值，避免"query A与chunk B语义不匹配但chunk B对query C高度相关"的情况
- **过滤阈值策略**：
  - rerankScore ≥ 0.7：主证据（Primary），直接采纳
  - 0.5 ≤ rerankScore < 0.7：候补证据（Secondary），最多保留2条
  - rerankScore < 0.5：直接丢弃
- **titlePath加权**：如果chunk的章节路径（titlePath）与查询词重叠度>50%，给予最多×1.10的加权

### 2.4 多查询融合策略

对于对比分析和研究类问题，采用多查询融合策略：

1. 生成多个不同角度的查询（通过Rewrite或Decompose生成）
2. 所有查询并行检索
3. 按chunkId去重（保留最高分），合并所有命中
4. Rerank阶段使用多查询评分取最大值

案例：问题"比较Qdrant和Milvus在性能和部署上的差异"
- 查询1："Qdrant 性能 QPS 延迟"
- 查询2："Milvus 性能 查询延迟 吞吐量"
- 查询3："Qdrant 部署 安装 运维"
- 查询4："Milvus 部署架构 组件 依赖"
- 检索结果合并去重后进行Rerank，各候选chunk取4个查询中的最高分

## 三、生成效果优化

### 3.1 提示词工程

RAG场景中的Prompt设计原则：

- **指令前置**：系统角色和任务指令放在最前面
- **上下文居中**：检索到的文档放在中间，分段清晰标注来源
- **问题置底**：用户问题放在最后，引导模型基于上下文回答
- **诚实性要求**：明确要求模型在上下文不包含相关答案时如实说明，不编造
- **引用标注**：要求模型在回答中标注信息来源（如"[1]根据XX文档..."）

Linsor AI的典型Prompt结构：
```
System: 你是Linsor AI的智能助手。基于以下上下文回答问题...
        如果上下文中没有相关信息，请诚实说明。
        [知识库检索结果]
        [KB-1] 文档：XXX
        [内容]......
        ---
        [KB-2] 文档：YYY
        [内容]......
        ---
        [联网搜索结果（如启用）]
        [Web-1] 标题 | URL
        [内容]......
User: [原始问题]
```

### 3.2 检索不足的应对策略

当检索质量审计（Audit）判定检索结果不足时，采取分层应对：

1. **第一层：改写重试（Retry with Rewrite）**
   - 采用更激进的改写策略：使用同义词替换、去除约束性过滤词、从更宽泛的角度切入
   - 最多重试2次

2. **第二层：网络搜索兜底（Web Search Fallback）**
   - 如果启用了网络搜索且仍有重试配额，调用Web Search进行补充
   - 将网络搜索结果标注为"[Web来源]"，与知识库结果区分

3. **第三层：诚实告知**
   - 重试次数耗尽后，仍然生成回答，但明确告知用户"当前知识库信息不足以完整回答此问题"

### 3.3 事实校验与完整性检查

**事实校验（Fact Check）**：
- 使用独立的LLM调用，逐条检查生成答案中的事实陈述是否能在检索上下文中找到支撑
- 输出每个陈述的风险等级（low/medium/high），以及是否需要修正
- 识别并标记答案中的推测性表述（"可能""应该""大概"等）

**完整性检查（Completeness Check）**：
- 将原始问题与生成的答案进行比对
- 识别答案中缺失的关键维度（如对比分析缺了某一方的信息、缺少性能数据等）
- 若覆盖率<80%且缺失维度可通过检索补充 → 触发补充检索和补充生成

## 四、性能与成本优化

### 4.1 Embedding缓存策略

相同内容的Embedding结果可以缓存复用：
- 使用SHA-256对chunk内容计算哈希，作为缓存键
- 缓存在Redis中（设置合理的过期时间，如7天）
- Linsor AI实现了此策略：`embed:{sha256_hash}` → 向量JSON
- 缓存命中跳过API调用，直接使用缓存向量，降低API成本并加速处理

### 4.2 检索结果缓存

对于高频、重复的查询，可以缓存检索结果。但需注意缓存失效策略：
- 文档更新时使相关查询的缓存失效
- 短查询（<10个字符）使用更短的TTL（查询意图不明，缓存命中率低且占用空间）
- 记录缓存命中率以评估缓存策略的有效性

### 4.3 模型选择与负载分级

不同处理阶段使用不同规格的模型以优化延迟和成本：
- **路由/改写/审计节点**：使用qwen-turbo（轻量模型），非流式调用，timeout=15s
- **生成节点**：使用qwen-plus（主力模型），流式输出，timeout=60s
- **事实检查/完整性检查**：使用qwen-turbo，非流式结构输出，timeout=15s

这种分级策略使整个RAG链条的总成本和延迟保持在可接受范围内，同时保证了最终答案的质量。

### 4.4 并发与批量优化

- 稠密检索和稀疏检索并行执行（Promise.all），而非串行
- 多查询的Embedding批量送入API（embedDocuments自动做批次管理），而非逐条调用
- LLM调用中的流式输出（Streaming）使首个token延迟降至最低，改善用户体验
- 使用AbortSignal处理客户端断开连接，避免已无用的LLM调用继续消耗资源

## 五、实验评估最佳实践

### 5.1 对比实验设计原则

进行RAG方案对比实验时，应遵循以下原则：
- **控制变量**：三组实验使用相同的知识库、相同的测试问题，仅改变检索和生成策略
- **覆盖全类型**：测试问题应均匀覆盖事实查询、对比分析、开放研究和问候四种类型
- **记录原始输出**：不仅记录统计指标，还要保留每条问题的完整答案，以便后续做RAGAS评估
- **频控与重试**：遵守API的速率限制（如10次/分钟），避免因频控导致的结果偏差

### 5.2 评估维度

| 维度 | 指标 | 测量方法 |
|------|------|----------|
| 检索效率 | hitCount, retrievalDuration | 脚本自动记录 |
| 生成效率 | generationDuration, totalDuration | 脚本自动记录 |
| 答案质量 | Faithfulness, Answer Relevancy | RAGAS人工或自动评估 |
| 答案完整性 | coverage, supplementTriggered | 观察是否触发补充检索 |
| 鲁棒性 | errorRate, retryCount | 统计错误和重试次数 |

### 5.3 常见问题排查

- **检索返回0条结果**：检查scoreThreshold是否过高、Embedding模型是否正常、Qdrant collection是否存在
- **答案质量差但与上下文一致**：问题在检索阶段（chunk不相关），需要优化改写策略或调整检索参数
- **答案捏造信息（幻觉）**：检查Prompt是否包含了"上下文中无相关信息时诚实说明"的指令
- **大量触发改写重试**：可能知识库与问题领域不匹配，需要在实验前确保知识库内容覆盖了问题范围
