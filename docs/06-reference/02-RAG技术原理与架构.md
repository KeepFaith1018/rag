# RAG（检索增强生成）技术原理与架构

## 一、RAG的定义与动机

检索增强生成（Retrieval-Augmented Generation，RAG）是一种将信息检索与文本生成相结合的技术范式，由Meta AI（当时为Facebook AI）在2020年首次正式提出。RAG的核心思想是在LLM生成回答之前，先从外部知识库中检索相关文档片段，然后将检索结果作为上下文提供给LLM，使其能够基于外部知识生成更准确、更可靠的回答。

RAG的动机源于LLM的三大局限性：
1. **知识截止问题**：LLM的知识在训练时就已固定，无法获取训练后的新信息
2. **幻觉问题**：LLM可能生成听起来合理但事实错误的内容
3. **领域知识不足**：通用LLM在垂直领域的专业知识可能不够深入

通过RAG，用户可以将私有文档、专业文献、最新资讯等外部知识注入LLM的生成过程，而无需对模型进行昂贵的微调或重新训练。

## 二、RAG系统架构

一个完整的RAG系统通常包含两个核心阶段：离线索引阶段和在线查询阶段。

### 2.1 离线索引阶段（Indexing Pipeline）

离线阶段的目的是将文档语料转化为可检索的向量索引：

```
原始文档 → 文档解析（PDF/MD/TXT等） → 文本分块（Chunking）
→ 文本向量化（Embedding） → 向量索引存储（Vector DB）
```

**文档解析**：支持多种格式（PDF、Markdown、Word、HTML、TXT等），需要处理表格、图片、代码块等特殊内容。PDF解析是最具挑战性的，因为PDF格式不保留段落结构，且公式、表格的提取常常失真。现代文档解析工具（如Mammoth、PyMuPDF、Unstructured.io）能够较好地保留文档结构。

**文本分块（Chunking）**：将长文档切分为适当大小的文本片段。分块策略直接影响检索质量——块太大则检索粒度不够精细，太小则上下文信息不足。常见策略包括：
- 固定长度分块（Fixed-size）：每块固定200/500/1000 tokens，简单但可能截断语义
- 语义分块（Semantic）：基于段落、章节、句子边界切分，保留语义完整性
- 递归分块（Recursive）：先按大分隔符（如"##"标题）拆分，过长则按次大分隔符（如"\n\n"）继续拆分
- 结构化分块（Structured Token-Aware）：考虑文档结构（标题层级、列表、代码块）和token密度，动态调整块大小。Linsor AI采用此策略，生成的chunk带有sectionLevel、blockType等元数据，便于后续的检索质量评估和加权

**文本向量化（Embedding）**：使用Embedding模型将文本片段转换为高维向量（通常1024-4096维）。常用模型包括OpenAI text-embedding-3-large（3072维）、阿里云 text-embedding-v4（1024维）、BGE-M3（1024维）。向量的余弦相似度反映了文本之间的语义相似程度。文本片段的向量被存储在向量数据库中，同时保留原始文本内容和元数据（如文档标题、页码、章节路径等）。

**元数据存储**：文档的元数据（标题、作者、创建时间、处理状态等）通常存储在关系型数据库中。Linsor AI使用MySQL（Prisma ORM）存储文档元数据，Qdrant存储向量索引，两者通过chunk ID关联。

### 2.2 在线查询阶段（Query Pipeline）

在线阶段的流程可以概括为：

```
用户问题 → 查询处理（路由/改写） → 混合检索（Dense+Sparse）
→ RRF融合 → 重排序（Rerank） → 上下文构建 → LLM生成答案
```

**查询处理**：
- **查询路由（Query Routing）**：判断问题类型（事实查询/对比分析/开放研究/问候），决定后续处理策略。问候类问题直接跳过检索，进入生成阶段
- **查询改写（Query Rewriting）**：将口语化、模糊的用户问题改写为更精准的检索查询。例如，"Doris怎么存数据比较快？" → ["Apache Doris 数据存储优化方法", "Doris 写入性能提升策略"]
- **查询分解（Query Decomposition）**：对于复杂的多维度对比问题，将其拆解为多个独立的子问题分别检索

**混合检索（Hybrid Retrieval）**：
- **稠密检索（Dense Retrieval）**：将改写后的查询向量化，在Qdrant中通过余弦相似度搜索top-K个最相似的文档片段（通常K=20-50）。稠密检索擅长捕捉语义相关性，即使关键词不匹配也能找到相关内容
- **稀疏检索（Sparse Retrieval）**：基于Elasticsearch的关键词/BM25检索。善于精确匹配专业术语、代码片段、人名地名，是稠密检索的重要补充。例如搜索"HAVING clause"时，关键词匹配比语义匹配更精确
- 两路检索并行执行，获得各自的候选集

**RRF融合（Reciprocal Rank Fusion）**：将稠密检索和稀疏检索的结果按照排名进行融合。RRF公式为：

```
RRF_score(d) = Σ 1/(k + rank_i(d))
```

其中k为平滑因子（典型值为60），rank_i(d)是文档d在第i路检索结果中的排名（从1开始）。RRF的优势在于它只需要排名而非原始分数，因此不受各路检索分数尺度差异的影响。Linsor AI在此基础上引入了基于Shannon熵的置信度加权机制——熵越低（分数分布越集中），该路检索的权重越高。

**重排序（Rerank）**：使用专门的Rerank模型（如qwen3-rerank、bge-reranker-v2）对融合后的候选片段进行深度语义精排。Rerank模型以[query, document]对作为输入，输出精确的相关性分数，远优于简单的向量相似度分数。Rerank阶段通常将50-80个候选片段精排为最终的5-15个片段。

**上下文构建与生成**：精排后的片段按照相关性排序，拼接为上下文文本。LLM基于"[系统提示] + [检索上下文] + [用户问题]"的三段式结构生成答案。为防止检索结果质量过低导致错误答案，现代RAG系统还会在生成前进行检索相关性审计（Audit）——判断检索结果是否充分覆盖了用户问题的信息需求，不够则触发改写重试或网络搜索兜底。

## 三、RAG技术演进

### 3.1 Naïve RAG（基础RAG）

最简单的RAG范式：用户问题 → 单次检索（仅稠密检索或仅关键词） → 取top-N片段 → 直接拼接为上下文 → LLM生成。Naïve RAG实现简单但存在明显不足：无法处理复杂查询、检索精度有限、缺乏质量评估。

### 3.2 Advanced RAG（高级RAG）

在Naïve RAG基础上增加了三个关键优化：
1. **查询处理**：引入查询改写和查询分解，将模糊的用户意图转化为精准的检索查询
2. **混合检索 + RRF融合**：结合稠密检索和稀疏检索的优势，提升召回率
3. **Rerank精排**：通过专门的Rerank模型提升最终结果的精度

Advanced RAG在回答质量上显著优于Naïve RAG，特别是对于对比分析和开放研究类问题。

### 3.3 Agentic RAG（智能体RAG）

引入多智能体（Multi-Agent）编排架构，将RAG流程建模为一个状态图（State Graph），每个节点代表一个专门的智能体：
- **Router Agent**：问题意图识别和类型分类
- **Rewriter Agent**：查询改写，将口语化表达转为检索友好格式
- **Decomposer Agent**：复杂问题的分解
- **Retriever Agent**：执行混合检索并返回精排结果
- **Auditor Agent**：检索质量审计（信息充分性判断）
- **Writer Agent**：基于检索上下文生成流畅、准确的回答
- **Fact Checker Agent**：事实核查，验证生成答案与检索来源的一致性
- **Completeness Checker Agent**：完整性检查，识别答案中缺失的关键信息维度

Agentic RAG通过LangGraph等工具构建有向图，定义了节点间复杂的条件跳转逻辑。例如：检索不足 → 触发改写重试（最多两次）；仍不足且有网络搜索能力 → 触发Web搜索兜底；答案不完整 → 触发补充检索和补充生成。这种编排使RAG系统具备了自我评估和自我修正的能力。

## 四、RAG评估体系

### 4.1 RAGAS评估框架

RAGAS（RAG Assessment）是当前最主流的RAG评估框架，从三个维度评估RAG质量：
- **Faithfulness（忠实度）**：生成的答案是否忠实于检索到的上下文（事实一致性）。对每个陈述逐一检查是否能在检索上下文中找到支撑
- **Answer Relevancy（答案相关性）**：答案是否直接回应了用户的问题。通过反向生成——"从这个答案可以推断出什么问题？"——来评估
- **Context Relevancy（上下文相关性）**：检索到的文档片段中与问题相关的比例。惩罚检索到了大量无关内容的情况

### 4.2 实验评估指标

在实际RAG系统开发中，常关注的量化指标包括：
- **hitCount**：单次查询检索到的有效文档片段数量
- **精确率（Precision）**：检索结果中相关片段的比例
- **召回率（Recall）**：所有相关片段中被检索到的比例
- **MRR（Mean Reciprocal Rank）**：第一个相关结果的排名倒数均值
- **生成延迟**：从接收问题到输出完整答案的总耗时，包含检索耗时和生成耗时
- **答案长度**：生成答案的总字符数或token数，间接反映答案的详细程度

## 五、RAG的典型应用场景

1. **企业知识库问答**：将企业内部文档（制度、流程、技术文档）构建为可问答的知识库。客服人员和新员工可以通过自然语言查询获取精准答案
2. **学术研究辅助**：研究者将论文集合作为知识库，快速检索和比较不同论文中的方法和结论
3. **法律/医疗文档分析**：精确检索法规条款或医学文献，辅助专业人士做决策
4. **代码库问答**：将代码仓库的文档和源码作为知识库，开发者可以询问架构设计、API用法等问题
5. **个人知识管理**：将笔记、阅读材料等构建为个人知识库，形成"第二大脑"
