# 向量数据库与检索技术

## 一、向量数据库概述

向量数据库是专门用于存储、索引和检索高维向量数据的数据库系统。在RAG领域中，向量数据库负责存储文档片段的Embedding向量，并提供高效的相似度搜索（Similarity Search）能力。

与传统的标量数据库不同，向量数据库的核心操作不是精确匹配，而是近似最近邻搜索（Approximate Nearest Neighbor，ANN）。给定一个查询向量，ANN算法在毫秒级时间内从数百万甚至数十亿向量中找出最相似的Top-K个结果。

## 二、主流向量数据库对比

### 2.1 Qdrant

Qdrant是一个用Rust编写的高性能向量数据库，以易用性和生产级可靠性著称。在Linsor AI中被选用为向量存储引擎。

**核心特性**：
- 支持多种向量相似度度量：余弦相似度（Cosine）、欧氏距离（Euclidean）、点积（Dot Product），默认使用余弦相似度
- HNSW（Hierarchical Navigable Small World）索引算法：平衡查询速度和召回率。通过`m`参数控制每个节点的连接数（默认16），`ef_construct`控制构建时的搜索深度（默认100），`ef`控制查询时的搜索深度（默认128）
- Scalar Quantization（标量量化，int8）：将float32向量压缩为int8，节省约75%存储空间，同时保持95%以上的召回率。Linsor AI使用quantile 0.99的标量量化配置，即99%分位数的值被保留
- Payload索引：支持对向量附带的元数据（如kbId、docId、chunkLevel）建立关键字索引，实现过滤式搜索（Filtered Search）
- 磁盘存储（Memmap）：支持将索引存储在磁盘上，突破内存限制

**性能指标（单机SSD，100万条1024维向量）**：
- 单次查询延迟：<10ms（p95）
- 每秒查询数（QPS）：200-500（取决于ef参数）
- 召回率（Recall@10）：>99%（ef=128时）
- 写入吞吐：约5000条/秒

### 2.2 Milvus

Milvus是由Zilliz开发的云原生向量数据库，采用存算分离架构。

**核心特性**：
- 支持IVF_FLAT、IVF_SQ8、HNSW、DiskANN等多种索引类型，根据场景灵活选择
- 存算分离：查询节点（Query Node）和数据节点（Data Node）独立水平扩展，适合超大规模部署
- 支持标量和向量混合查询（Hybrid Search），可在一次查询中同时进行属性过滤和向量搜索
- 多向量字段支持（Multi-Vector）：同一个Collection中可以存储多个不同的向量字段
- 一致性级别可配置：从最终一致到强一致，满足不同场景需求

**与Qdrant的对比**：
| 维度 | Qdrant | Milvus |
|------|--------|--------|
| 开发语言 | Rust | Go/C++ |
| 部署复杂度 | 低（单二进制文件） | 中高（多组件依赖，需etcd/MinIO/Pulsar） |
| 适合场景 | 中小规模（百万~亿级向量） | 大规模（十亿级以上） |
| 资源消耗 | 低（内存友好，支持磁盘存储） | 较高（多组件运行开销） |
| 全文搜索 | 不内置（需结合ES） | 不内置（需结合ES） |
| 社区活跃度 | 快速增长 | 成熟稳定，企业用户多 |

### 2.3 Weaviate

Weaviate是一个开源的向量搜索引擎，内置了向量化和混合搜索能力。

**核心特性**：
- 内置向量化模块：可以直接调用OpenAI、Cohere、HuggingFace等Embedding API，无需额外的向量化流程
- Hybrid Search原生支持：将BM25稀疏检索和向量稠密检索在同一个查询中融合，通过alpha参数（0-1）控制两种检索的权重比例
- GraphQL API：所有操作（CRUD、搜索）都通过GraphQL接口，具有灵活的查询表达能力
- 多模态支持：文本、图片等多模态向量可以共存于同一schema中

**与Qdrant的对比**：
| 维度 | Qdrant | Weaviate |
|------|--------|----------|
| API风格 | REST + gRPC | GraphQL + REST |
| 向量化 | 需外部服务 | 内置模块 |
| 混合搜索 | 需结合外部ES | 原生BM25+向量融合 |
| 生态集成 | 灵活，与LangChain/LlamaIndex集成度高 | 内置向量化，开箱即用 |
| 过滤查询 | Payload索引（简单高效） | GraphQL过滤（表达力强但复杂） |
| 推荐场景 | 已有独立的Embedding和ES管线的系统 | 需要一站式向量+关键词检索的系统 |

### 2.4 选型总结

- **推荐Qdrant**：需要高性能、低运维负担、已有独立Embedding服务的场景。特别适合Linsor AI这类已有完整检索管线的系统
- **推荐Milvus**：需要处理十亿级以上向量数据、需要存算分离弹性扩展的企业级应用
- **推荐Weaviate**：需要快速搭建原型、希望一站式解决向量化和混合搜索的小型团队

## 三、近似最近邻（ANN）算法

### 3.1 HNSW算法详解

HNSW（Hierarchical Navigable Small World）是当前最主流的ANN索引算法之一，被Qdrant、Weaviate等数据库采用。

HNSW构建了一个多层图结构：
- 底层（Layer 0）包含所有数据节点
- 上层随机抽取部分节点（概率由层衰减因子m_L控制），构成稀疏图
- 搜索从最顶层的入口点开始，逐层向下贪心逼近，在每层找到局部最近节点后下降到下一层
- 到底层时已完成粗筛，进行精细搜索

**关键参数**：
- m（连接数）：每个节点在图中与其他节点建立的连接数。默认16。越大则召回率越高但内存开销越大
- ef_construct（构建搜索深度）：构建索引时搜索的候选队大小。默认100。越大索引质量越高但构建越慢
- ef（查询搜索深度）：查询时维护的动态候选队列大小。默认128。越大召回率越高但查询越慢。Linsor AI使用ef=128

HNSW的时间复杂度为O(log N)，空间复杂度为O(N * m)。

### 3.2 IVF（Inverted File Index）算法

将向量空间划分为若干个聚类（Cluster），查询时仅搜索最近的N个聚类（nprobe参数控制搜索范围）。IVF适合对召回率要求不那么严格的高吞吐场景，但需要训练的聚类中心。

### 3.3 DiskANN

DiskANN是微软开发的面向磁盘存储的ANN算法。通过Vamana图索引将大多数数据存储在SSD上，仅将少量导航数据保留在内存中，大幅降低内存成本。适合超大规模（十亿级以上）且内存受限的场景。

## 四、Elasticsearch稀疏检索

在RAG混合检索中，Elasticsearch（ES）作为稀疏/关键词检索的引擎，补充稠密向量的语义检索。

### 4.1 BM25算法

BM25（Best Match 25）是ES默认的相关性评分算法，是TF-IDF的改进版本。公式为：

```
BM25(q, d) = Σ IDF(qi) * (tf(qi, d) * (k1 + 1)) / (tf(qi, d) + k1 * (1 - b + b * |d| / avgdl))
```

其中k1控制词频饱和度（默认1.2），b控制文档长度归一化程度（默认0.75）。BM25相比TF-IDF的改进：词频饱和处理（出现20次的词不会得到10次词的双倍分数）和文档长度归一化（长文档不会因包含更多词而天然获得更高分数）。

### 4.2 在RAG中的角色

- 精确匹配专业术语、代码标识符、版本号、人名、地名等（稠密检索可能因训练语料中少见而向量表示不佳）
- 多词查询的精确召回
- 与稠密检索互补：稠密找"意思相似的"，稀疏找"精确匹配的"

Linsor AI的稀疏检索服务（ElasticsearchSparseRetrievalService）将改写后的查询中的关键词提取出来作为ES查询输入，与稠密检索并行执行。ES不可用时降级为空结果，不中断整个检索流水线。

## 五、标量量化（Scalar Quantization）

为了降低向量存储成本并提升检索速度，现代向量数据库广泛采用量化技术。

**int8标量量化**：
- 将float32向量（每维4字节）压缩为int8（每维1字节），存储缩减75%
- 原理：找到向量的[min, max]范围，均匀映射到[0, 255]整数区间。使用quantile（如0.99）排除极端值，避免量化误差过大
- 量化误差通常控制在2%以内，召回率损失可忽略
- Qdrant默认启用int8标量量化，配置为`scalar: { type: 'int8', quantile: 0.99, always_ram: true }`
- `always_ram: true`表示量化后的向量仍保留在内存中以确保检索速度

**乘积量化（Product Quantization，PQ）**：
- 将向量分割为多个子向量，对每个子空间独立聚类和量化
- 压缩率更高（可压缩至原始大小的5-10%），但召回率损失也更大（通常3-8%）
- 适合对存储成本极其敏感的超大规模场景（十亿级以上）

## 六、Payload索引与过滤检索

在RAG场景中，向量检索常常需要结合元数据过滤。例如，仅在特定知识库（kbId）内搜索，或仅搜索特定文档（docId）的片段。

Qdrant通过Payload索引实现此能力：
```json
// 在搜索时指定过滤条件
{
  "filter": {
    "should": [
      { "key": "kbId", "match": { "value": "123" } },
      { "key": "kbId", "match": { "value": "456" } }
    ]
  }
}
```

在过滤条件存在时，Qdrant使用两阶段检索：先通过payload索引筛选符合条件的点，再在这些点中进行向量搜索。这比先进行向量搜索再按metadata过滤要高效得多。Linsor AI为`kbId`、`docId`、`chunkLevel`三个字段创建了payload关键字索引。
