# Linsor AI 系统架构

## 总体结构

Linsor AI 使用 pnpm monorepo：

```text
apps/
├── server/  # NestJS API、任务处理、RAG 和后台管理
└── web/     # Vue 用户界面
```

核心基础设施：

| 组件 | 用途 | 默认端口 |
|---|---|---:|
| MySQL | 业务元数据 | 13306 |
| Qdrant | 稠密向量 | 16333/16334 |
| Elasticsearch | 稀疏索引 | 19200 |
| Redis | BullMQ、缓存和会话辅助 | 16379 |
| MinIO | 对象存储 | 19000/19001 |

## 后端分层

```text
apps/server/src/
├── common/   # Prisma、缓存、向量库、存储、Guard、异常、日志
└── modules/
    ├── auth/
    ├── user/
    ├── email/
    ├── knowledge-base/
    ├── document/
    ├── rag/
    ├── chat/
    ├── admin/
    └── health/
```

控制器负责 HTTP 契约，Service 负责业务规则，Prisma 负责元数据持久化。Qdrant 和 Elasticsearch 通过公共基础设施服务访问，Redis 为 BullMQ 和缓存提供支持。

## 前端分层

```text
apps/web/src/
├── api/          # 请求、Token 刷新与接口封装
├── stores/       # Pinia 状态
├── router/       # 路由和登录守卫
├── views/        # auth、chat、kb 页面
├── modules/      # chat、document-upload
├── components/   # UI 和业务组件
└── composables/  # 通用组合逻辑
```

前端通过普通 JSON API 管理资源，通过原生 SSE 接收 AG-UI 对话事件。Incremark 负责增量 Markdown，Shiki 负责代码高亮。

## 文档入库数据流

```text
上传/分片合并
  → MySQL 创建文档记录
  → BullMQ 入队
  → 解析
  → 结构感知分块
  → Embedding
  → Qdrant 稠密索引
  → Elasticsearch 稀疏索引
  → 文档 ready
```

MySQL 保存文档、Chunk 元数据和任务状态；Qdrant、Elasticsearch 保存可重建索引。

## 在线问答数据流

```text
问题
  → 权限与模型配置解析
  → LangGraph 路由/拆解/重写
  → Qdrant + Elasticsearch 检索
  → 融合与重排
  → 必要时重试或联网搜索
  → 流式生成
  → 保存消息与引用
  → 异步质量评估
```

## 核心设计边界

- MySQL 是业务元数据事实来源。
- Prisma Schema 和 migrations 是数据库结构事实来源。
- Qdrant 与 Elasticsearch 数据必须能够从 MySQL 文档和 Chunk 重建。
- BullMQ 任务必须携带 `processingVersion`，旧版本结果不得覆盖新版本。
- 知识库访问必须由后端 Guard 和权限服务校验。
- AG-UI 是前后端流式事件契约，事件类型集中维护。
- 离线评估不阻塞用户接收主回答。
