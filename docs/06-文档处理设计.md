# Linsor AI 文档处理设计

## 主流程

```text
uploaded → parsing → chunking → embedding → ready
```

文档创建后写入 MySQL并提交 BullMQ 任务。Worker 在后台执行解析、分块、Embedding、Qdrant 写入和 Elasticsearch 写入，上传请求不等待处理完成。

## 任务与版本

- 每次首次处理或重解析都有 `processingVersion`。
- Worker 开始和各阶段写入前必须确认任务版本等于文档当前版本。
- 旧版本任务停止处理，不得覆盖新状态或索引。
- `b_document_processing_tasks` 记录阶段、状态、尝试次数、开始/结束时间、心跳和错误。
- Monitor 定时扫描心跳超时任务并将其置为失败。

## 解析

解析服务按文件类型提取文本和结构信息。解析结果保留标题层级、块类型、页码或字符位置等可用来源信息。无意义的二进制片段、异常长串和空内容应在进入分块前过滤。

## 分块

系统使用结构感知、token 约束的多层分块：

- 上层 Chunk 表达章节或较完整语义。
- Level 3 子 Chunk 用于 Embedding 和精确检索。
- Chunk 保存父子关系、标题路径、块类型、token 数和来源位置。
- 超长结构块继续切分，缺少结构时使用通用文本分块兜底。

## Embedding 与索引

1. 选取可嵌入的子 Chunk。
2. 批量调用 Embedding 服务。
3. 校验向量数量和维度。
4. 写入 Qdrant。
5. 写入 Elasticsearch。
6. 保存索引标识并将文档标记为 `ready`。

任一步失败都应保留明确阶段和错误信息，不得错误推进到 `ready`。

## 删除与重解析

### 删除

- 校验知识库和文档权限。
- 删除 Qdrant points。
- 删除 Elasticsearch documents。
- 删除本地文件和关联数据库记录。
- 跨存储操作失败时记录可恢复信息。

### 重解析

- 递增 `processing_version`。
- 清理旧 Chunk 和外部索引。
- 重置文档处理状态。
- 提交携带新版本的任务。

## 进度与可观测性

- API 可查询文档详情和阶段任务。
- SSE 推送处理状态和进度。
- 日志包含文档 ID、处理版本、阶段、attempt 和耗时。
- 超时阈值与扫描周期由环境变量控制。

## 一致性原则

- MySQL 是文档与 Chunk 元数据事实来源。
- 外部索引必须可重建。
- 状态更新必须与当前处理版本绑定。
- 重试必须幂等，重复执行不得产生重复 Chunk 或向量。
