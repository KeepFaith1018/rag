# Linsor AI 前端优化 — 分析与建议

> 基于项目全面分析，按照性能、体积、架构、可维护性四个维度梳理优化机会。
> 生成日期：2026-05-08

---

## 一、性能优化

### 1.1 highlight.js 全量引入 → 按需加载

**现状**：`useStreamingMarkdown.ts` 使用 `import hljs from 'highlight.js'` 全量引入（~1.2MB 包含 190+ 语言）。

**影响**：首次加载体积大，影响 Lighthouse 评分。

**建议方案**：
- 方案 A：仅注册常用语言（ts/js/python/shell/json/markdown/sql 等约 8 种），手动 `hljs.registerLanguage()`
- 方案 B：动态 import `highlight.js/lib/core` + 按需注册，将 hljs 从主包分离
- 预期减少 ~800KB gzipped

### 1.2 Material Symbols 字体加载策略

**现状**：通过 `material-symbols` npm 包 + CSS `@font-face` 加载完整图标字体文件。

**影响**：字体文件 ~500KB+，可能阻塞首屏渲染。

**建议方案**：
- 评估是否可迁移到 `@iconify/vue` 按需图标，或使用 SVG sprite
- 如保留字体方案，设置 `font-display: swap` + preload 关键字符集

### 1.3 字体文件体积

**现状**：`@fontsource/inter` + `@fontsource/space-grotesk` 完整引入。

**建议方案**：
- 按需引入字重（当前使用了哪些？）
- 考虑使用 `subset` 版本（仅拉丁字符）
- 预加载关键字体

### 1.4 路由懒加载 — 已完成

**现状**：所有页面组件已使用动态 `import()`，✅ 无需优化。

### 1.5 ChatStream 滚动性能

**现状**：`MutationObserver` 监听 `subtree: true` + `characterData: true`，高频率流式更新时可能有抖动。

**建议方案**：
- 增加 throttle（requestAnimationFrame 限流）
- 或改用 CSS `scroll-behavior: auto` + 手动 `scrollTop` 赋值
- 当前实现相对简洁，如无明显性能问题可维持

### 1.6 API 序列化开销

**现状**：`api.ts` 中每次请求都对 body 做复杂的类型判断（`shouldSerializeJsonBody` / `isNativeBodyInit` / `shouldSetJsonContentType`）。

**建议方案**：
- 这是一个很小的开销，目前无需优化
- 如果未来有高频短请求场景，可缓存判断结果

## 二、打包体积优化

### 2.1 依赖分析

**当前关键包 (估算)**：

| 包 | 估算 gzip | 必要性 |
|---|---|---|
| vue + vue-router + pinia | ~40KB | 必需 |
| highlight.js (全量) | ~120KB | 可大幅缩减 |
| marked | ~35KB | 必需 |
| material-symbols | ~30KB | 可优化 |
| Inter 字体 | ~50KB | 可做 subset |
| Space Grotesk 字体 | ~40KB | 可做 subset |
| @vueuse/core (仅用 2 个函数) | tree-shakeable | 实际很小 |

**建议**：
1. `pnpm build` 后可运行 `pnpx vite-bundle-visualizer` 或类似工具生成可视化报告
2. 重点检查 tree-shaking 是否生效

### 2.2 clsx + tailwind-merge 使用情况

**现状**：`package.json` 中有声明，但代码中几乎未使用。

**建议**：
- 如确实未用，从 `package.json` 中移除
- 或在需要处使用（如 `BaseButton` 的 class 合并）

## 三、架构优化

### 3.1 ChatStore 职责过于集中

**现状**：`stores/chat.ts` 703 行，包含会话管理 + 消息管理 + Agent 状态 + 模型/知识库选择 + 步骤/工具记录全部逻辑。

**建议**：
- 不急于拆分 — 当前 store 虽然大但逻辑内聚
- 如果后续增长到 1000+ 行，考虑拆为 `chatSessionStore` + `chatAgentStore`

### 3.2 KbDetailView 页面过于庞大

**现状**：1650 行，三 tab 全部内联在一个组件中。

**建议**：
- 将三个 tab 拆为独立组件：`DocumentsTab.vue`、`MembersTab.vue`、`SettingsTab.vue`
- `KbDetailView.vue` 仅作为编排容器，负责数据加载与 tab 切换
- 收益：可测试性提升、按需加载、可读性改善

### 3.3 重复的 `resolveErrorMessage` 逻辑

**现状**：`LoginView.vue` / `ForgotPasswordView.vue` / `KbListView.vue` / `KbDetailView.vue` / `useChunkUpload.ts` 中各有独立的错误文字解析函数。

**建议**：
- 提取到 `src/utils/error-message.ts` 统一引用
- 避免重复代码，统一错误消息格式

### 3.4 重复的表单校验逻辑

**现状**：`LoginView.vue` 和 `ForgotPasswordView.vue` 有相同/相似的 `validateEmail`、`validatePassword`、`validateVerificationCode`。

**建议**：
- 提取到 `src/utils/validators.ts` 作为纯函数

## 四、可维护性优化

### 4.1 TypeScript strict 模式

**现状**：`tsconfig.app.json` 中已启用 `noUnusedLocals`、`noUnusedParameters`、`noFallthroughCasesInSwitch`、`erasableSyntaxOnly`，✅ 已较好。

**建议**：考虑启用 `strict: true`（目前继承自 `@vue/tsconfig/tsconfig.dom.json`，需确认其配置）

### 4.2 组件 Props 类型

**现状**：已使用 `defineProps<T>()` + `withDefaults`，✅ 类型安全较好。

### 4.3 CSS 变量命名一致性

**现状**：Tailwind v4 `@theme` + Tailwind v3 兼容配置 (`tailwind.config.js`) 双轨运行。

**建议**：
- 确认 `tailwind.config.js` 是否仍在使用（Tailwind v4 主要通过 CSS 配置）
- 如 v4 完全生效，可移除 `tailwind.config.js`

### 4.4 错误边界

**现状**：无全局错误边界组件。

**建议**：
- 添加 `onErrorCaptured` 钩子到 `App.vue`
- 可选使用 `vue:error-boundary` 组件包裹关键区域
