# 传统 RAG 痛点与本项目优化演进

## 1. 传统 RAG 是什么

传统 RAG（Retrieval-Augmented Generation）是最基础的检索增强生成范式：

```
用户提问 → 直接 Embedding → 向量检索 → 直接送给 LLM 生成答案
```

---

## 2. 传统 RAG 的十大痛点

### 痛点一：Query 直接检索，"垃圾进垃圾出"

**问题**：用户问题往往是口语化的、多义的、或者缺少关键检索词。

```
用户问："那个去年Q3销量最好的产品叫什么来着"
直接 embedding: "那个去年Q3销量最好的产品叫什么来着" → 语义偏移严重
```

**本项目解决**：Query Rewriting

```
用户提问
    ↓
[Rewriter Agent] - LLM 重写为 1~3 个更精准的查询
    ↓
"2024年第三季度销量最高的产品"（去掉口语、补充主谓）
"Q3 2024 sales top product"（中英双语扩展）
    ↓
多个查询同时检索，扩大命中范围
```

---

### 痛点二：复杂问题被粗暴对待

**问题**：用户的 `"对比苹果和华为的Mate系列手机"` 被当作简单事实查询处理。

**本项目解决**：Query Decomposition

```
[Decomposer Agent] 将复杂问题拆分为子问题：
┌─────────────────────────────────────┐
│ 原始问题：对比苹果和华为的Mate系列手机 │
├─────────────────────────────────────┤
│ 子问题1：苹果Mate系列的主要型号和配置   │
│ 子问题2：华为Mate系列的主要型号和配置   │
│ 子问题3：两者在价格/性能/拍照的对比    │
└─────────────────────────────────────┘
    ↓
并行检索每个子问题，结果融合后回答
```

---

### 痛点三：单一检索模式，召回率低

**问题**：纯向量语义检索对专有名词、数字日期检索效果差。

```
用户问："基于transformer架构的模型有哪些"
语义检索：embedding 偏移 → 召回困难

纯关键词：transformer 架构 模型 → 可以召回，但无语义理解
```

**本项目解决**：Hybrid Retrieval（稠密 + 稀疏混合检索）

```
查询同时走两条路：
┌─────────────────┐     ┌──────────────────────┐
│  Dense Retrieval │     │   Sparse Retrieval   │
│  (向量语义相似度) │     │   (关键词 LIKE 匹配)  │
└────────┬────────┘     └─────────┬──────────┘
         │                          │
         ▼                          ▼
┌────────────────────────────────────────────┐
│           RRF Fusion (互惠排名融合)           │
│  score = Σ 1/(k + rank_i)  k=60           │
│  平衡语义相关性和关键词匹配                   │
└────────────────────────────────────────────┘
```

---

### 痛点四：检索结果无质量验证

**问题**：检索到内容后直接喂给 LLM，不验证是否真的相关。

**本项目解决**：Relevance Check（相关性检验）

```
[Verifier Agent] 评估检索结果与问题的相关性：
┌─────────────────────────────────────────────┐
│ 问题："公司年营收增长率是多少"              │
│ 检索结果 chunk1: "公司成立于2018年..."      │ → not_relevant
│ 检索结果 chunk2: "2024年年营收1000万..."   │ → relevant
│ 检索结果 chunk3: "产品线包括ABC三条..."     │ → not_relevant
└─────────────────────────────────────────────┘
    ↓
如果大量 not_relevant → 自动重试/重写查询
```

---

### 痛点五：LLM 生成无事实校验

**问题**：LLM 可能"幻觉"，生成与检索内容不符的答案。

**本项目解决**：Fact Check（事实校验）

```
[Verifier Agent] 对生成内容逐句核查：
┌─────────────────────────────────────────────┐
│ 生成答案："公司2024年营收增长50%"           │
├─────────────────────────────────────────────┤
│ 证据 chunk1: "2024年营收1000万，增长50%"    │ → supported ✓
│ 证据 chunk2: "2023年营收800万"             │ → supported ✓
│ 证据 chunk3: "公司成立于2018年"             │ → not_verified
└─────────────────────────────────────────────┘
    ↓
如果 contradicted（矛盾）→ 标记 needRevise，触发修订
```

---

### 痛点六：答案完整性无保证

**问题**：LLM 可能只回答了问题的部分方面，用户问的是 A+B，答案只有 A。

**本项目解决**：Completeness Check（完整性检查）

```
[Verifier Agent] 检查答案覆盖度：
┌─────────────────────────────────────────────┐
│ 问题："对比苹果和华为的Mate系列"            │
├─────────────────────────────────────────────┤
│ 答案覆盖了：✓ 型号对比 ✓ 性能对比           │
│ 缺失了：✗ 价格对比 ✗ 拍照对比 ✗ 续航对比   │
├─────────────────────────────────────────────┤
│ overallCoverage: 40% → needSupplement: true │
└─────────────────────────────────────────────┘
    ↓
触发补充检索，找到缺失方面的信息
```

---

### 痛点七：无重试机制，一次失败全盘失败

**问题**：传统 RAG 检索不到就直接返回"未找到相关信息"。

**本项目解决**：Fallback + Retry Loop

```
fallbackCount < 2?
    │
    ▼ Yes
┌─────────────────────────────────┐
│ relevance_check = not_relevant  │
│ fallbackCount++                 │
│ 触发 rewrite_query 重新检索       │
└─────────────────────────────────┘
    │ No
    ▼
直接结束（避免无限循环）
```

---

### 痛点八：无意图分类，"一把梭"

**问题**：简单问候和复杂研究问题走同样的流程，浪费资源。

**本项目解决**：Query Router（意图路由）

```
[Router Agent] 分类用户意图：
┌─────────────────────────────────────────────┐
│ greeting       → 直接回复问候，跳过检索      │
│ fact_lookup    → 单次检索，直接生成          │
│ compare_analysis → 查询分解 + 多路检索      │
│ research_or_open_world → 深度搜索 + 验证   │
└─────────────────────────────────────────────┘
    ↓
不同意图走不同流程，优化响应速度和资源消耗
```

---

### 痛点九：无引用追踪，答案可信度低

**问题**：用户无法验证答案来源，不知道是不是瞎编的。

**本项目解决**：Citation Service（引用服务）

```
答案中嵌入引用标记：
"根据《2024年年度报告》[1]，公司营收增长50%。其中，
Q1营收300万[2]，Q2营收400万[3]，Q3营收... "

引用记录包含：
- 知识库名称、文档标题
- 具体 chunk 内容（前200字符）
- 重排分数（相关性量化指标）
```

---

### 痛点十：无法处理需要推理的复杂查询

**问题**：用户的 `"为什么去年Q3那个产品销量突然下滑"` 需要推理，不是直接检索能解决的。

**本项目解决**：Agent State Graph + 多 Agent 协作

```
┌─────────────────────────────────────────────────────┐
│              Multi-Agent Orchestrator                │
├─────────────────────────────────────────────────────┤
│                                                      │
│  Planning Phase（规划阶段）                          │
│    route_query → rewrite_query → decompose_question │
│         │              │              │               │
│         ▼              ▼              ▼               │
│  Retrieval Phase（检索阶段）                         │
│    dense + sparse → fusion → rerank → relevance    │
│         │                                          │
│         ▼                                          │
│  Verification Phase（验证阶段）                     │
│    fact_check + completeness_check                  │
│         │                                          │
│         ▼                                          │
│  Writing Phase（写作阶段）                           │
│    基于完整上下文生成最终答案                        │
│                                                      │
└─────────────────────────────────────────────────────┘

状态在节点间传递，每阶段都是独立 LLM 调用
```

## 3. 架构演进对比

### 传统 RAG（0.0 版本）
```
User Query → Embed → Retrieve → LLM → Response
           单一流程，无任何优化
```

### 本项目 RAG（Multi-Agent 版本）
```
User Query
    │
    ▼
┌──────────────────────────────────────────────────────┐
│  Router Agent                                        │
│  判断意图类型（greeting/fact/compare/research）      │
└──────────────────────┬───────────────────────────────┘
                       │
        ┌──────────────┴──────────────┐
        ▼                              ▼
┌───────────────┐            ┌─────────────────────┐
│ Simple Path   │            │ Complex Path        │
│ (fact_lookup) │            │ (compare/research)  │
├───────────────┤            ├─────────────────────┤
│ 1. Rewrite   │            │ 1. Rewrite (×1-3)  │
│ 2. Retrieve  │            │ 2. Decompose (×N)  │
│ 3. Generate  │            │ 3. Multi Retrieve  │
└───────────────┘            │ 4. Relevance Check │
                            │ 5. [Retry Loop]     │
                            │ 6. Fact Check       │
                            │ 7. Completeness Ck  │
                            │ 8. Generate         │
                            └─────────────────────┘
    │
    ▼
┌──────────────────────────────────────┐
│  Citation Service                    │
│  持久化引用，记录分数和来源             │
└──────────────────────────────────────┘
    │
    ▼
Response (带引用、可信、可验证)
```

## 4. 关键优化点总结

| 痛点 | 传统 RAG | 本项目解决方案 |
|------|----------|----------------|
| Query 质量 | 直接检索 | Router + Rewriter |
| 复杂问题 | 简单处理 | Decomposer 分解 |
| 召回率 | 纯向量 | Hybrid + RRF Fusion |
| 结果验证 | 无 | Relevance Check |
| 幻觉风险 | 无 | Fact Check |
| 答案完整 | 无 | Completeness Check |
| 失败重试 | 无 | Fallback + Retry |
| 意图分流 | 无 | Router 分类 |
| 引用追踪 | 无 | Citation Service |
| 推理能力 | 无 | Multi-Agent StateGraph |

---

## 5. 未来优化方向

1. **Web Search 集成**：当知识库内容不足时，自动触发网络搜索
2. **Cross-Encoder Rerank**：用 Cohere/BGE-Reranker 替代当前简单文本重叠评分
3. **Embedding 缓存**：相同文本避免重复 Embedding，节省 API 调用
4. **流式监控完善**：心跳超时清理长时间处于 streaming 状态的孤儿消息
5. **Agent Step 完整持久化**：每步 LLM 输入输出完整记录到 `b_agent_steps` 表
