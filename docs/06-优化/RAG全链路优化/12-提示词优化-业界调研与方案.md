# 全系统提示词优化 — 业界调研与方案

> 调研日期：2026-05-09 | 范围：chunk/chat/prompts 下全部 8 个 prompt 文件

## 一、业界最佳实践

### 1.1 查询改写（Query Rewrite）

| 来源 | 核心方法 | 关键结论 |
|------|---------|---------|
| LevelRAG (AAAI 2025) | 稀疏检索器需关键词级查询（Extend/Emphasize/Filter） | 优化查询改写比调 Embedding 模型 ROI 更高 |
| MaFeRw (AAAI 2025) | 多维反馈强化学习优化改写器 | 改写质量需要从检索+生成两个维度反馈 |
| SynRewrite (2025) | LLM 生成的合成改写优于人工改写 | 用 GPT-4o 生成训练数据训练 Flan-T5 改写器 |
| 腾讯云工业实践 | "去口语化 + 关键词提取" Prompt 模板 | 将"大白话"翻译为"搜索关键词" |

**标准改写 Prompt 结构**：

```
Role: 查询重写专家
1. 消歧义：代词 → 具体实体
2. 去噪：去掉"帮我查"/"我想知道"等引导词
3. 关键词化：口语 → 专业术语（"连不上网" → "网络连接故障"）
4. 多视角扩展：生成 3 个不同维度查询（精准匹配/语义扩展/问题拆解）
Output: { "rewritten_queries": [...], "keywords": [...] }
```

### 1.2 事实审核（Fact Check）

| 来源 | 核心方法 | 关键结论 |
|------|---------|---------|
| Domres et al. (2025) | 原子事实分解 + Few-Shot + 循环修正 | 4-shot 比 1-shot 提升显著；逐条 supported/contradicted/not_verified |
| Ewe Framework (Meta 2025) | 生成中实时事实检查 | Working Memory 暂停生成逐句检查 |
| Hybrid Fact-Check (EMNLP 2025) | KG + LLM + Web Search 三层 | F1=0.93 无微调 |

**原子事实 Prompt 关键要素**：
- 拆解为独立可验证的原子陈述
- 逐条对照检索证据判断 supported/contradicted/not_verified
- 提供 Few-Shot 示例（至少 1 个 supported + 1 个 contradicted + 1 个 not_verified）

### 1.3 完整性校验（Completeness）

| 来源 | 核心方法 | 关键结论 |
|------|---------|---------|
| CaSE (2025) | 因果逐步评估 | 评估推理链相关性和连贯性 |
| 企业实践 | 回扣查询拆解的子问题列表对照检查 | 比自由评估更准确 |

**关键改进**：completeness_check 应收到 decompose 拆解出的子问题列表，逐条对照检查覆盖度。

### 1.4 Prompt 工程通用原则

| 原则 | 说明 |
|------|------|
| 结构化输出 | 用 Schema 约束输出格式，prompt 中不必重复描述字段 |
| Few-Shot > Zero-Shot | 验证类任务给示例显著提升准确率 |
| 量化阈值 | "大多数"→"≥2 条相关"；避免模糊判定标准 |
| Prompt 压缩 | JSON 格式说明占大量 token，可从 prompt 移到 Schema |

## 二、当前系统 Prompt 审计

### 2.1 逐文件诊断

| Prompt | 核心问题 | 严重度 | 优化方向 |
|--------|---------|:--:|------|
| **rewrite** | 生成完整长句，缺乏短关键词；无字数限制 | 🔴 | 增加 keywords 输出 + ≤15 字约束 + Few-Shot |
| **decompose** | keywords 已输出但 **未被 buildRetrieveQueries 使用** | 🔴 | keywords 送入检索 |
| **router** | intent 和 questionType 完全同构，重复输出 | 🟡 | 合并字段 |
| **audit** | 判断标准模糊，"sufficient"门槛无量化 | 🟡 | 加 0-hit→insufficient 规则（已做） |
| **relevance** | 无量化阈值（"大多数"是几个？） | 🟡 | `relevant: ≥2; partial: 1; not_relevant: 0` |
| **fact_check** | 无 Few-Shot 示例，contradicted/not_verified 边界模糊 | 🟡 | 加 3 个示例 |
| **completeness** | 未回扣 decompose 子问题，coverage 评分偏高 | 🟡 | 传入 subQueries 列表 |
| **writer** | 补充内容可能重复主回答 | 🟢 | 补充 prompt 加"不重复已有内容" |

### 2.2 共性问题

1. **JSON 格式说明占 30-50% token 预算** — Zod Schema 已定义字段，prompt 中可精简
2. **全部 Zero-Shot** — 无任何 Few-Shot 示例
3. **边界判定靠 LLM 自觉** — 缺数量化阈值
4. **decompose 的 keywords 被丢弃** — LLM 帮你做的关键词提取没用到

## 三、优化方案

### Phase 1：检索命中率（改 2 文件）

**rewrite.prompt.ts**：

```
改动: 增加 keywords 字段 + 长度限制 + Few-Shot 示例

输出新增:
  "keywords": ["构建工具", "Webpack", "Vite", "Rollup"]

Prompt 增加:
  - 每条查询 ≤15 字，使用关键词组合
  - 示例: 正确: "前端构建工具链 Webpack Vite" / 错误: "现代前端工程化体系中的构建工具链包括哪些内容？"
```

**multi-agent-orchestrator.service.ts**：

```
改动: buildRetrieveQueries 增加 decompose 的 keywords

现有: queries = [originalQuery, ...decomposedQueries, ...rewrittenQueries]
改为: queries = [originalQuery, ...decomposedQueries, ...rewrittenQueries, ...allKeywords]
```

### Phase 2：校验准确性（改 4 文件）

| 文件 | 改动 |
|------|------|
| relevance-check | 增加量化阈值说明：`relevant: ≥2 条相关; partial: 1 条; not_relevant: 0 条` |
| fact-check | 增加 3 个 Few-Shot 示例（1 supported + 1 contradicted + 1 not_verified） |
| completeness-check | 传入 decompose 的子问题列表，改为逐条对照检查 |
| router | 合并 intent 和 questionType 为单一字段 |

### Phase 3：Token 精简（改全部文件）

- JSON 格式说明精简为 `"按 JSON 格式输出，字段定义见 Schema"`
- 移除与 Zod Schema 重复的字段描述
- 预计平均节省 30-40% token

## 四、与业界对齐度评估

| 维度 | 业界标准 | 当前系统 | 差距 |
|------|---------|---------|:--:|
| 查询改写 | 多查询 + 关键词提取 | 多查询但无关键词提取 | 🔴 |
| 关键词利用 | decompose 的关键词入检 | 关键词丢弃未用 | 🔴 |
| Few-Shot | 校验类至少 3 示例 | 全部 Zero-Shot | 🟡 |
| 量化阈值 | 明确数值标准 | 模糊描述 | 🟡 |
| 子问题回扣 | completeness 回扣 decompose | 独立判断 | 🟡 |
| Prompt 压缩 | Schema 与 Prompt 分离 | 大量重复描述 | 🟢 |
| HyDE | 生成假设答案辅助检索 | 未实现 | 🟢 |
| RAGAS 评估 | 离线定量评估 | 无 | 🟢 |
