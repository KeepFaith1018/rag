# 流式 AI 回复处理 & Agent 流程渲染 — 技术选型

> 调研日期：2026-05-08 | 实施日期：2026-05-08 | 状态：已完成实施
> 适用范围：前端 apps/web，替换 highlight.js 为 Shiki，保留 marked 解析

---

## 一、问题定义（修正）

深入分析 `useStreamingMarkdown.ts` 的 `tryFlush()` 后，发现当前 marked 方案采用 buffer 切片策略（每次 flush 后切走已解析部分），**并非 O(n²)**。主要技术债实际为：

1. **highlight.js 体积大**：全量引入 ~200KB+，语法高亮质量一般
2. **无流式高亮**：代码块必须等完整后才能高亮
3. marked 解析性能在当前切片策略下已可接受

1. **Markdown 解析 O(n²)**：每次 `tryFlush()` 都调用 `marked.parse()` 全量解析整个 buffer，随 AI 输出增长重复解析量指数上升
2. **代码高亮体积大**：`highlight.js` 全量引入 ~200KB+，且无流式高亮能力

## 二、分层选型

### 2.1 流式协议解析（前端 ↔ 后端通信）

| 方案 | 适配度 | 说明 |
|------|--------|------|
| **保持自研 AG-UI 解析** | ★★★★★ | 后端已深度绑定 AG-UI 协议 (NestJS SSE)，前端 `useAgentChat.ts` 解析逻辑清晰 |
| Vercel AI SDK (`@ai-sdk/vue`) | ★★ | 要求后端使用 `streamText` + `toUIMessageStreamResponse` 格式，与现有 AG-UI 不兼容，需全量改造后端 |
| CopilotKit | ★★ | React 生态为主，Vue 支持薄弱，后端协议也需改造 |

**选择：保持自研 AG-UI 解析。**

AG-UI (Agent-User Interaction Protocol) 是公开标准协议，被 AutoGen、CopilotKit 等采纳。当前 `useAgentChat.ts` 中对 `RUN_STARTED/STEP_STARTED/TOOL_CALL_START/TEXT_MESSAGE_CONTENT` 等事件类型的解析逻辑稳定、可控，无需为追新而替换。Vercel AI SDK 虽流行（450K+ 月下载），但其协议层与 AG-UI 不兼容，迁移成本远大于收益。

### 2.2 增量 Markdown 渲染（核心优化点）

传统解析器在流式场景下的 O(n²) 问题：

```
Chunk 1: parse 100 chars
Chunk 2: parse 200 chars (100 old + 100 new) ← 冗余
Chunk 3: parse 300 chars (200 old + 100 new) ← 冗余
...
Chunk 100: parse 10,000 chars
Total: ~5,050,000 字符操作 / 10KB 文档
```

#### 候选方案

| 方案 | 解析模式 | Vue 支持 | 体积 | 成熟度 | 综合评价 |
|------|---------|---------|------|--------|---------|
| **Incremark** | 真增量 O(n) | Vue 3 适配器 | ~15KB | 2025 新项目，活跃 | ★★★★★ |
| markstream-vue | 全量 O(n²) + 虚拟滚动 | Vue 3 原生 | ~20KB | 成熟 | ★★★★ |
| marked (当前) | 全量 O(n²) | 自研封装 | ~35KB | 成熟 | ★★ |
| ant-design-x | 全量 O(n²) | React 专属 | 大 (antd) | 企业级 | ★★ |

#### Incremark 工作原理

```
文本流输入: "## Title\n\nParagraph text\n\n```js\ncon"
                                    │
                          ┌─────────┴─────────┐
                          │  检测稳定边界       │
                          │  (空行/标题/代码    │
                          │   块闭合等)         │
                          └─────────┬─────────┘
                                    │
                    ┌───────────────┼───────────────┐
                    │               │               │
              已完成块(缓存)    待定块(重新解析)   新 token
              ┌──────────┐   ┌──────────────┐   ┌──────┐
              │"## Title"│   │"```js\ncon"  │   │sole. │
              │"Paragrap"│   │(代码块未闭合) │   │log()"│
              └──────────┘   └──────────────┘   └──────┘
                    │               │
                    └───────┬───────┘
                            │
                    合并输出 HTML
                   (已完成块不重新解析)
```

- 基于**稳定边界检测**：空行、ATX 标题 (`#`)、代码围栏 (` ``` `) 闭合视为稳定点
- 已完成块仅解析一次并缓存，后续增量只处理末尾未稳定块
- 双引擎：marked（默认，快速）+ micromark（严格 CommonMark 合规）

#### 选择：Incremark

理由：
- **真增量解析 O(n)**：长文档可达 46 倍性能提升（官方 benchmark），本项目对话场景 AI 输出越长收益越大
- **标准 mdast AST 输出**：与 remark 生态兼容
- **Vue 适配器原生支持**：Vue 3 Composition API，无需自研封装
- **代码块生命周期回调**：`onCodeBlockStart` / `onCodeBlockEnd`，可精确对接 shiki-stream 流式高亮

备选 markstream-vue 更成熟（内置虚拟滚动、Mermaid 渐进渲染），但底层仍是全量解析 O(n²)，不适合本项目 AI 输出可能较长的场景。

### 2.3 代码块语法高亮

| 方案 | 体积 | 高亮质量 | 流式能力 | 综合评价 |
|------|------|---------|---------|---------|
| **Shiki + shiki-stream** | ~15KB 核心 + 按需语言 | ★★★★★ VS Code 同款 | ✅ 原生流式 | ★★★★★ |
| highlight.js 按需 | ~30KB + 8 种语言 ~40KB | ★★★ | ❌ | ★★★ |
| highlight.js 全量 (当前) | ~200KB+ | ★★ | ❌ | ★ |

#### Shiki 流式高亮原理 (shiki-stream)

```
代码 token 流 → CodeToTokenTransformStream → ThemedToken 事件流
                                               │
                              ┌────────────────┼────────────────┐
                              │                │                │
                         Stable Token     Unstable Token    Recall Token
                        (完整行，直接渲染) (末尾未完成行)   (前文 token 类型
                                                            需修正时回退替换)
```

- Anthony Fu (Vue/Vite 核心团队成员) 开发，专为 LLM 输出场景设计
- **Stable/Unstable 分离**：完整行视为 stable 立即输出，末尾不完整行标记为 unstable 可能被后续召回修正
- **RecallToken 机制**：后续上下文导致之前 token 分类变化时，发出召回通知让渲染端回退替换（例如多行注释的识别）
- 已被 Cherry Studio 等 AI 客户端项目采用

#### 选择：Shiki + shiki-stream

理由：
- **流式高亮原生支持**：与 Incremark 的代码块生命周期回调天然配合 — 代码块开始时创建 shiki-stream 实例，逐 token 累积高亮，代码块结束时分段输出高亮 HTML
- **体积可控**：核心 ~15KB + 按需加载语言包（本项目主要涉及 ts/js/python/shell/json/markdown/sql/yaml 约 8 种，每种 ~3-8KB gzip）
- **VS Code 同款质量**：TextMate 语法引擎，双主题（明暗）原生支持，可复用项目现有的 `primary` 色调

备用方案：highlight.js 按需注册 8 种语言（~40KB）。不保留当前全量加载（200KB+）。

### 2.4 Agent 流程可视化

| 方案 | 适配度 | 说明 |
|------|--------|------|
| **保持自研** | ★★★★★ | `ChatAgentTimeline.vue` + `AIMessageItem` 中的 AG-UI 步骤面板 |
| assistant-ui (Vue port) | ★★★ | 社区移植 `@assistant-ui/vue`，依赖 shadcn/ui 样式体系，与本项目设计语言冲突 |
| React Flow + dagre | ★★ | DAG 图可视化，适合复杂多分支 agent 拓扑，不适合本项目的线性流水线 |

**选择：保持自研。**

当前 `ChatAgentTimeline.vue` 的 6 阶段指示器（planning→retrieving→reranking→verifying→writing→done）+ `AIMessageItem.vue` 中的 AG-UI 步骤面板已经良好实现了 agent 流程可视化，且使用项目自身的 CSS 变量主题体系，不需要引入外部 UI 库的样式依赖。

## 四、风险与回退

| 风险 | 概率 | 应对 |
|------|------|------|
| Incremark 社区小，有 bug | 低 | 源代码 ~2000 行可自行维护；回退到 marked 仅需恢复 useStreamingMarkdown.ts |
| Shiki + shiki-stream 体积仍超预期 | 低 | 回退到 highlight.js 按需加载方案 |
| 与现有 Agent 状态管理冲突 | 极低 | 两库均只替换 `useStreamingMarkdown.ts`，不涉及 chatStore 或 Agent 逻辑 |

迁移改造范围局限在一个文件（`useStreamingMarkdown.ts`），回退成本极低。
